# 生图历史

本文描述用户主动留存同步生图结果时的业务规则、捕获范围、数据所有权和失败边界。本文不覆盖批量图片作业，也不恢复已经下线的自研异步图片任务或旧 `image_storage` 配置。

## 核心语义

生图历史有两层开关：部署者必须先通过进程配置启用 `image_history` 并提供完整的私有 S3 兼容存储，用户再在面板中主动开启个人保存选择。用户字段 `save_image_history` 默认 `false`；只有全局存储可用且该字段为 `true` 时，后续符合范围的成功生图请求才会进入捕获链路。关闭保存不删除已有记录，删除必须由用户逐条执行。

全局配置关闭时，设置接口仍可返回 `available=false`，但不能把用户选择改为开启；列表、下载和删除按功能不可用处理。重新启用全局配置不会迁移对象或改变既有用户字段。

管理员可在设置页的“文件存储”顶级标签中维护生图历史的 S3 连接和图片目录前缀。页面配置是数据库覆盖，保存后热生效；删除覆盖或覆盖读取失败时回退到 YAML/环境变量部署配置。该覆盖只作用于生图历史，备份、发票附件和数据共享仍沿用各自的存储配置和目录，旧部署未配置页面覆盖时行为保持不变。

## 捕获范围

当前捕获范围是经 TokenRouter 网关完成的同步 OpenAI Images、OpenAI Responses、Grok 图片生成/编辑和 Gemini 原生 `generateContent` 图片请求，包括普通 JSON、SSE，以及 OAuth/Antigravity 路径内部聚合出的最终图片响应。捕获器接受最终 `b64_json`、图片 URL、Gemini `inlineData` 或等价最终结果，忽略 partial image，并在单次请求内按图片引用去重。

批量图片作业、视频、聊天响应中没有图片生成结果的请求，以及已下线的异步图片任务不进入该历史。历史捕获发生在网关原响应已经成功处理之后，不参与账号选择、上游重试、计费或客户端响应形状。

## 保存链路

请求开始时，handler 仅为已主动开启的用户创建请求级捕获器；响应转换层把最终图片引用写入捕获器。请求完成后，handler 把图片和用户、API Key、请求 ID、来源、endpoint、模型及 prompt 元数据非阻塞提交给进程级有界 worker 队列。

worker 对 base64 结果直接解码，对临时 HTTPS URL 使用不读取环境代理且拒绝私网、回环、链路本地、组播和未指定地址的专用 HTTP client 下载。转存前按实际字节解码 PNG、JPEG、WebP 或 GIF 格式，取得尺寸并计算 SHA-256；声明的 MIME 只作为输入提示，不能覆盖实际格式。单对象字节数、下载超时、任务总超时、worker 数和队列容量由 `image_history` 进程配置限制。

## 数据与访问边界

PostgreSQL 的 `image_histories` 表只保存当前用户归属、可空 API Key 归属、请求和模型元数据、提示词、非敏感生图参数 JSON、私有对象键、实际 MIME、字节数、尺寸、SHA-256 与创建时间。参数快照包含模型、尺寸、质量、数量、响应格式、背景、输出格式、审核、风格、输入保真度以及 Grok 的分辨率/时长等选项，不包含原始请求体中的输入图片字节或凭据。对象键使用独立前缀并按用户和 UTC 年/月分层；图片字节只保存在配置的 S3 兼容桶中，不能与备份、数据共享或旧异步图片前缀混用。

列表按创建时间倒序分页，支持对模型、提示词、来源、接口和请求 ID 的不区分大小写模糊搜索；每个对象尽力生成短期预签名预览 URL，单个签名失败不会让整页失败。鉴权下载先按当前用户查询元数据，再由后端代理私有对象，并使用服务端生成的安全文件名。删除同样先校验用户归属，先删对象再删元数据，避免数据库删除成功后留下用户不可见的计费对象。

## 失败与一致性

历史保存是 fail-open 的旁路能力：队列满、任务超时、下载失败、格式或大小不合法、S3 故障、元数据写入失败都只记录后台错误，不改变已经返回的生图结果或计费。一个请求包含多张图片时逐张保存，单张失败不会回滚同请求中已经成功的图片。

对象上传成功但元数据写入失败时，服务使用独立短超时尝试删除刚上传的对象；清理再次失败仍可能产生孤儿对象，运维应通过 `image_history.save_failed` 和对象存储清单发现并处理。进程关闭时停止接收新任务并取消正在执行的转存，队列不是持久任务系统，不能承诺重启后补传。
